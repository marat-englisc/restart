> [!abstract] Коротко
> **Роль** — набор прав на объекты конфигурации (чтение, добавление, изменение, проведение…). **Пользователю** назначают одну или несколько ролей; права ролей **складываются**. Скрытая кнопка или отбор списка — не защита: защищают только права и **ограничения доступа к данным (RLS)**.

## Роли

**Общие → Роли → Добавить**:

![[Pasted image 20260917155625.png]]

*Роль «Администрирование»: слева дерево объектов, справа права на выбранный объект, ниже — ограничения доступа к данным.*

| Элемент окна | Назначение |
| --- | --- |
| **Объекты** (слева) | Дерево конфигурации: выбираем объект, права на который настраиваем |
| **Права** (справа) | Список прав для выбранного объекта |
| **Ограничения доступа к данным** | Условия на уровне записей и полей (RLS) |
| **Действия → Установить все права / Снять все права** | Быстро включить или отключить права |
| **Устанавливать права для новых объектов** | Новые объекты конфигурации сразу получат права в этой роли — для обычных ролей лучше не включать |
| **Устанавливать права для реквизитов и табличных частей по умолчанию** | Не настраивать права для каждого реквизита отдельно |

На корне конфигурации задаются общие права: **Администрирование**, **Тонкий клиент**, **Веб-клиент**, **Вывод** (печать, копирование), **Сохранение данных пользователя** и др.

> [!warning] Права запуска клиента
> Если у пользователя ни в одной роли нет права «Тонкий клиент» (или «Веб-клиент») на корне конфигурации, он не сможет войти в программу этим клиентом.

### Основные и интерактивные права

| Вид | Примеры | Когда проверяются |
| --- | --- | --- |
| **Основные** | Чтение, Добавление, Изменение, Удаление, Проведение | При **любом** обращении к данным — и из кода, и из интерфейса |
| **Интерактивные** | Интерактивное добавление, Интерактивное удаление, Интерактивная пометка удаления, Просмотр, Редактирование | Только при действиях пользователя в интерфейсе |

Интерактивное право работает лишь вместе с соответствующим основным. Например, можно разрешить **Удаление** (чтобы удаляла служебная обработка), но запретить **Интерактивное удаление** — пользователь не нажмёт `Shift+Del` сам.

> [!tip] Хороший тон
> Делаем **маленькие ролевые блоки** без дублирования: «ЧтениеНСИ», «ДобавлениеИзменениеЗаказов», «ПроведениеНакладных». Пользователю назначаем набор таких ролей. Так проще сопровождать права, чем десяток «почти одинаковых» больших ролей.

> [!info] Пользователи в типовых конфигурациях
> В решениях на БСП пользователей создают в самом Предприятии (**Администрирование → Пользователи**), а права — через **группы доступа** и **профили**. Конфигуратор для этого не используют.

> [!warning] Первый пользователь
> Пока в базе нет ни одного пользователя, вход выполняется без авторизации с полными правами. Как только создан первый пользователь, вход возможен только под существующими пользователями. Первым создаём администратора с ролью, содержащей право «Администрирование».

## Несколько ролей — права складываются

Разрешения ролей **объединяются**: если хоть одна роль разрешает изменение, отсутствие права в другой роли его не отнимает. Роль `ТолькоЧтение` не ограничит пользователя, у которого есть ещё и `ПолныеПрава`. «Запрещающих» ролей в 1С нет.

## Права ≠ интерфейс

> [!warning] Важно
> Скрытая кнопка, `ТолькоПросмотр` у поля или отбор списка **не заменяют права**. Данные можно получить через другой интерфейс, отчёт или код. Защита строится ролями.

В коде права проверяют так:

```1C
Если НЕ ПравоДоступа("Изменение", Метаданные.Документы.РасходнаяНакладная) Тогда
	ВызватьИсключение "Недостаточно прав для изменения накладных";
КонецЕсли;

Если РольДоступна("Администрирование") Тогда ...
```

Подробнее, включая привилегированный режим, — [[05. Профессиональная разработка/05. Права доступа и RLS в коде|Права доступа и RLS в коде]].

## Как проверять роль

1. Создаём учебного пользователя только с проверяемыми ролями.
2. Запускаем **новый сеанс** под ним (из Конфигуратора: **Сервис → 1С:Предприятие**, выбрав пользователя в окне входа).
3. Проверяем по задаче: открытие списка, чтение, создание, изменение, проведение, удаление, печать, отчёты.

Работа под администратором ничего не доказывает — у него есть всё.

## Ограничение по записям (RLS)

Иногда пользователь должен видеть **только документы своей организации**. Для этого существуют **ограничения доступа к данным на уровне записей** — условие на языке запросов, которое платформа добавляет к каждому чтению:

```text
РасходнаяНакладная ГДЕ РасходнаяНакладная.Организация = &ТекущаяОрганизация
```

Значение `&ТекущаяОрганизация` берётся из параметра сеанса ([[26. Функциональные опции и параметры сеанса]]). Отбор в списке такую защиту не обеспечивает: это лишь удобство интерфейса.

> [!question]- Проверь себя
> 1. У пользователя две роли: «ЧтениеЗаказов» и «ПолныеПрава». Сможет ли он удалить заказ?
> 2. Чем «Удаление» отличается от «Интерактивного удаления»?
> 3. Скрыли кнопку «Провести» в форме. Защищены ли документы от проведения?
>
> > [!success]- Ответы
> > 1. Да: права ролей складываются.
> > 2. «Удаление» действует при любом обращении (в том числе из кода), «Интерактивное удаление» — только для действий пользователя в интерфейсе.
> > 3. Нет. Нужно убрать право «Проведение» в ролях.
